All 377 cases pass together once the tree stops moving. The cause was not the code under test: `src/` and `tests/` were being rewritten **during** the runs. The files that moved are exactly the set the previous pass had edited, and they landed one at a time, minutes apart — `jobs/worker.py` at 16:06:54, `adapters/qlib/runtime.py` at 16:37:58 and again at 16:43:18 — each after the tests covering it had already been run and reported green. A 90-second content-hash sample of all 97 source/test/doc files caught `runtime.py` changing (`1a89c8043e79` → `f6915d7c0bae`, i.e. mid-sample). One of those late landings was a genuine regression: the version of `jobs/worker.py` that landed echoed the engine's raw stdout into `PipelineBlocked`, which `test_qlib_worker_preserves_safe_blocker_and_hides_unknown_output` rejects (see the note in [上线风险与修复方案](上线风险与修复方案.md)). It now logs the tail to the worker's own log and keeps the message safe, as the document already specified — the code had drifted from its own written contract. **Practical consequence for anyone re-running this suite: confirm the working tree's mtimes are stable first, then run it; otherwise a red run proves nothing.**

**The suite is also load-sensitive, and that is a property of the test fixture, not of the code under test.** `tests/conftest.py`'s `db` fixture truncates every public table at setup, which takes an `AccessExclusiveLock` on each; a case that still holds a row lock — a worker thread not yet drained, a second pooled connection — deadlocks with it, and a deadlock aborts the transaction. Running the same suite twice on an idle host, and again while the stack was rebuilding generations and repairing history, produced 369/2, 353/12 and (on the two heaviest files) 64/64. Two of this round's own cases were implicated and were rewritten to take a single transaction; an attempt to make the fixture retry deadlocks in a fresh transaction made things **worse** (44 failed, runtime doubled) and was reverted.

The 2 failures on the idle run are `test_scheduler_does_not_repeat_bulk_enqueue_work` and `test_scheduled_export_registers_a_sealed_generation`, both of which pass when `test_workflow_postgres.py` runs alone (92 passed).

**Run the suite against its own database.** Two `pytest` processes sharing one `quant_test*` database deadlock on the fixture's `TRUNCATE` (`AccessExclusiveLock` against a live row lock), raise `UniqueViolation` on `calendars_pkey`, and produce a *different* failing set each run — 69 failed, then 17 failed, then 6 failed, from the same code. A second database (`quant_test_<name>`, the same `postgres` container, the same forwarder) removes the whole class: the final run above is **377 passed, 0 failed** on a host that was simultaneously running a Qlib training job. **A red suite is not evidence until you have confirmed nothing else is using that database.**

## Deployed-stack defect closure and end-to-end run — 2026-09-26/27

Scope: the current working tree (Alembic `0010`) deployed with `deploy/compose.yaml` + `deploy/compose.local.yaml` on a macOS Apple Silicon host running Docker Desktop. **15/15 platform containers healthy**, plus a temporary `alpine/socat` port forward used only by the host suite. Single-operator development deployment: **not** production acceptance, and it does not demonstrate model performance, five-minute capacity, or off-host recovery.

The run had one purpose: close the defects that kept the deployed platform from ever producing a Qlib generation, then prove closure **against the running stack** rather than against fixtures. Images were rebuilt (`docker compose build migrate` and `build qlib-data`, then `up -d`), because the containers carry the packaged code and there is no source bind-mount.

### Defects found and fixed

1. **The collection window was one session too short, so the admission check could never be satisfied.** The price limits of the analysis window's *oldest* session are derived from that session's previous close, and that previous session lies outside the analysis window. Nothing collected it, so `constraints` could never cover the window, `source_gaps` always reported a gap, and the platform never published a generation. `jobs/scheduler.py` now adds exactly one lead-in session (`LEAD_IN_SESSIONS = 1`) to the collection window; the lead-in supplies a single close and is not itself a generation session, nor does it need a limit of its own.
2. **Widening the window did not re-fetch.** One request per security covers the whole window, so `completed_codes` — which only asks whether the *newest* session is in hand — called a security finished even when the request that produced it never reached the window's new first session. `collect.collected_through` records how far back an endpoint has ever been published and forces a full re-fetch whenever the window is wider than that.
3. **The capability gate was structurally unsatisfiable.** `readiness` requires all seven `DAILY_CAPABILITIES` to carry `schema_verified`. `Market._qualify` is keyed on the capability that issued the request, but `calendar` and `benchmark` are read out of `history`'s response and `factors` out of the paired request `_factors` makes, so none of the three ever reached `_qualify` under its own name; `security_history` is pure derivation with no probeable source at all. All four were therefore permanently `schema_verified=false`, and the platform reported itself blocked while it was in fact collecting — the two-session `qualification` gate could never open either. `Market._qualify_derived` now records the qualification at those three call sites, and `CAPABILITY_SOURCES["security_history"]` is `("derived",)`.
4. **`build_generation` demanded an adjustment factor on the window's oldest row.** Public sources publish a much shallower front-adjusted series than raw daily bars (腾讯 stops at ~800 sessions, see `factor_sessions`), so requiring the oldest row to be adjusted conflated "the factor becomes available from a later day" with "this security is unusable" and dropped whole securities from a pipeline generation. The normalization anchor now pins to the oldest *adjusted* row, the same row `write_bins` already used; unadjusted prices still never enter a generation.
5. **Retired native-analysis remnants.** `tests/test_research_path.py` imported `analysis.screen` and `analysis.research.evaluate`, both deleted, so the module failed at import; the replica/recovery cases it shared a file with moved to `tests/test_backup_replica.py`. `RuleInput` was removed from `api/__init__.py`: `PUT /rules` answers 410 for every request, and declaring the retired schema only turned a malformed body into a 422 describing a feature that no longer exists. Stale references to a native fallback were removed from the Qlib adapter messages, and the roadmap entries describing the retired path are marked cancelled rather than accepted. A dead-code scan over `src/` and `tests/` now reports no unreferenced module-level definition and no unused import; the only test-only symbols left are `external_features` / `external_universe`, which are the public API of the isolated Qlib research reader.
6. **Two test defects that only surface on a loaded or unlucky machine.**
   - `tests/test_workflow_postgres.py` derived T+1..T+3 from the **Beijing** date while `operations.maintenance` aligns partitions to the **UTC** calendar. The assertion passed for the 16 hours a day the two agree and failed for the other eight. It now reads the UTC date.
   - `tests/test_boundaries_dashboard.py` used `AppTest`'s 3-second default timeout, which the suite's first Streamlit script run exceeds on a loaded host; raised to the 15 seconds the rest of the file already uses.

### How the live run was driven

The daily plan is idempotent per Beijing day, so every dedupe key for 2026-09-27 already existed and the scheduler — correctly — enqueued nothing after the rebuild. The re-plan used the platform's own paths only: the `schedule:history` / `schedule:security` checkpoints were cleared and `POST /control {"action":"refresh"}` was issued, which re-runs `tick()` and enqueues fresh `calendar` and `securities` jobs; `POST /control {"action":"doctor"}` re-ran the capability probe; and one `benchmark` job was enqueued through the platform's own `Database.enqueue` for `analysis_target`, because the benchmark enqueue is gated behind the same daily checkpoint. No row was edited and no job was marked complete by hand.

### Deliberate behaviours recorded rather than changed

- **`coverage` in the generation manifest is keyed by the whole listed master, not by the collected scope.** Of its 5220 entries, 265 carry a last-covered date, 19 have bars but no factor, and 4936 have no bars at all and are reported as `missing_adjustment_or_bars`. That status string means "missing adjustment *or* bars", the entry set is stable regardless of index membership, and consumers already ignore non-date values (`qlib/report.py:coverage_window`). It is noisy but accurate, so it was left alone.
- **The pipeline path is blocked on a day whose decision date precedes the first security-state observation.** `security_states` holds 5220 rows, all `effective_day = 2026-09-26`, while `analysis_target` is `2026-09-24`; `build_generation` requires the state's `available_at` to be on or before the bar day, so `risk` is NaN for every bar, no security is `ready`, and `qlib_prepare` fails closed with `Qlib input coverage 0.0% is below policy`. Using a state observed after the decision date would be look-ahead, so this is the correct answer for a first run; it clears once the target advances past the observation day. The scheduled path (`qlib_export` → `qlib_report`) does not depend on security states and completed end to end.

- No Qlib model has been trained or approved, so `day` readiness is still `false` on that single, legitimate blocker. Re-attempt training once `analysis_target` advances past 2026-09-26.

### Defects found and fixed by this run

1. **pytdx private exceptions escaped the degradation chain.** `Tdx` only caught `OSError` around `connect`, and called `get_security_bars` / `get_security_quotes` / `get_security_list` with no guard at all. `pytdx` raises its own `TdxException` tree, so `ResponseHeaderRecvFails` bypassed `Market._degrade` and aborted the whole capability instead of trying the next source. Every pytdx call now goes through one guard that converts any client failure into `ProviderError`.
2. **The security master could not be published without 东方财富.** `instruments.list_date` was `NOT NULL`, but neither 通达信 nor 新浪 publishes a listing date, so the fallback master died on `NotNullViolation`. Migration `0009` makes the column nullable, the strict `list_date<=day` filters became NULL-tolerant (matching the convention the `analysis` layer already used), and the missing dates stay NULL with `list_dates_verified=false`.
3. **The morning refresh froze a half-formed daily bar.** Phase one renamed the `morning-factors` job to `morning-history` while changing its payload to `end=today`, so from 09:20 onward the platform wrote the current, still-trading session into `daily_bars` — which is `ON CONFLICT DO NOTHING`, so the partial bar would have persisted forever. `collect.history` now publishes a bar only for a session that has closed, and the morning job is a `factors` job that writes today's factor alone.
4. **`constraints` was not scoped like `history`.** It derived limits for every listed A-share while `history` collected only the scoped universe, so a default deployment immediately queued 1499 sessions × 5220 securities of requests that could never converge. `constraints` now uses `scoped_codes`, the same scope as `history`.
5. **Two test-fixture defects** that had never run because the PostgreSQL suite was always skipped: `history_rows`-based fakes omitted `pre_close` (which every real provider row carries), and the workflow fixture recorded a `security_states` row for a symbol the instrument table did not contain.
6. **The `db` fixture was plan-dependent.** It listed tables through the `pg_tables` view, whose `('public.'||tablename)::regclass` cast can be pushed below the view's own `schemaname='public'` filter; once it evaluated `pg_catalog.pg_statistic` the whole query failed with `relation "public.pg_statistic" does not exist`. It now reads `pg_class` + `pg_namespace` and never casts a name.
