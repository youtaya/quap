# QUAP 上线风险与修复方案

本文回答一个问题：**现在把这套系统拿去用，会在哪里出问题，怎么修。**

所有条目都基于 2026-09-26/27 在一台 macOS + Docker Desktop 上的**真实部署取证**（15/15 容器健康、Alembic `0010`），以及对本仓库代码的直接审阅。取证过程与原始数字见[系统验证报告](系统验证报告.md#deployed-stack-defect-closure-and-end-to-end-run--2026-092627)。

**分级**：

| 级别 | 含义 |
| --- | --- |
| **P0** | 直接阻塞上线：系统当前**产不出可用结果** |
| **P1** | 影响结论正确性：会产生前视偏差 / 样本偏差，或让使用者误读 |
| **P2** | 运维、安全与可用性：不影响当下计算，但会在故障或人员变动时咬人 |
| **P3** | 观测与语义：会误导判断，不改变计算结果 |

**先看结论**：本系统目前处于「**数据在采集、代次能产出、训练与评估能跑完，但还没有一个被批准的模型**」的状态。P0 全部集中在模型链路，P1 大部分集中在**点位（point-in-time）数据的缺失** —— 后者是这套免令牌公开源方案的固有代价，也是上线前最需要向使用方交代清楚的部分。

**训练链路已打通（本轮）**：覆盖率 0.0% → **98.99%**，`qlib_prepare` 与 `qlib_train` 都 `complete`，`pipeline_runs.state = succeeded`，产出的模型 `rank_ic = +0.0370` 但 `passed = false`。**拒绝它的那一条判据（`historical_pool_coverage_passed`）根因是 P1-4** —— 点位风险状态从数据层传播到了策略层。要拿到已批准的模型，必须先对 P1-4 做产品决策，详见 [P0-1](#p0-1-没有任何已训练已批准模型平台零产出)。

### 本轮（参考 QuantMind 与 microsoft/qlib 的实现）已修复

| 条目 | 修了什么 | 依据 |
| --- | --- | --- |
| **P1-2 上市日期** | 新增东方财富**数据中心主机**兜底源；真实源实测 5220 只 **100%** 拿到上市日期 | 关键是识别出「被拒的是**一台主机**，不是这家数据源」 |
| **P0-3 覆盖门禁** | 训练宇宙改为**等于采集范围**；新增独立的采集范围阻塞项 | 门禁的分母必须等于平台声称覆盖的范围 |
| **P0-2 训练阻塞（死结）** | **训练接受未知的点位风险状态**：观测日之前的历史 K 线风险特征是 NaN，不再因此把整批证券挡在代次之外；推断仍要求决策日当天的状态 | Qlib 的 NaN 语义：缺失特征交给模型，不丢整只证券。QuantMind BUG-11：缺列要**显式告警**，不是静默跳过 |
| **P0-2 月度回归** | 风险状态改为**按决策日**对采集范围观测一次（纯本地推导，不花配额）；月度全表扫描保留给范围外的历史证券 | 月度刷新会把状态钉在当月 1 日，1 日 18:30 之前的决策日再没有任何状态覆盖它 —— 覆盖率每月归零一次 |
| **P0-2 可诊断性** | 覆盖率不足时输出**排除理由分布**与成因说明，而不是一句 `coverage 0.0%` | QuantMind BUG-11：缺列要**显式告警**，不是静默跳过 |
| **P1-1 复权窗口深度** | 代次 manifest 新增 `coverage_detail.adjusted_window`（每只证券可用会话数的 min/中位/max、短于窗口的只数） | 深度与上市时间、流动性相关，是**非随机缺失**，必须可读 |
| **P1-5 停牌虚假断言** | `suspended` 由恒 `False` 改为 `None` + `suspended_source: "unavailable"`；报告区分「0 只停牌」与「未知」 | Qlib 约定：停牌在数据里是 **NaN**，不是一个布尔列 |
| **P1-6 无因子证券** | `data_quality.bars_without_any_adjustment` 给出数量与前 20 只名单 | 样本面无声缩小是最容易被漏掉的一类缺口 |
| **P3-1 覆盖率语义** | 代次 manifest 新增 `coverage_detail`：声明范围 / 合格数 / 就绪数 / **逐项排除理由** / 全市场占比（仅诊断） | 一个百分比无法行动，没被命名的缺口等于不存在 |
| **P3-2 数据健康语义** | 新增 `quiet_outside_session`：非交易时段且目录新鲜时不再报降级；日历未验证时不猜「休市」 | 周末长期告警会让这个字段彻底失去可信度 |

**未能修复的**：P1-3/P1-4（成分与风险状态的**带日期**历史）依赖**外部数据可得性**。本轮实测发现东方财富的 K 线与列表接口在本网络被网络边缘拒绝，这是环境约束，改代码解决不了 —— 详见 P0-3 与 P1-1。P1-7（IC 为负）需要先给出解释再决定是否动代码。

### 本轮在真实栈上**新发现**并修复的两个缺陷

这两个都不在原来的风险清单里 —— 它们只有在「采集补全、代次真的产出来、训练真的开始跑」之后才会露出来。它们同时也是「上一轮把 33 只缺口归因为环境约束」这个判断错了的证据。

| 缺陷 | 症状 | 修复 |
| --- | --- | --- |
| **保留策略删掉了被钉住的代次** | 导出端只留两代，而**流水线代次与导出代次落在同一个 `qlib/` 目录**，于是 `GenerationStore.publish()` 把运行已经钉住的那一代删掉；重试时报 `FileNotFoundError: /data/artifacts/qlib/generation-11a18ddc…` —— 在平台自己删掉的目录上崩溃 | `publish(stage, name, retain=…)`；`export()` 查两条钉住路径（`pipeline_steps.result.generation_id` 与 `snapshot.research_generation_id`）里 `waiting`/`running`/`blocked` 的运行，豁免它们引用的代次。保留仍然有界 |
| **引擎的失败原因被丢掉** | `jobs/worker.py` 对非 3 的退出码只报一句「Qlib engine step failed; inspect the generation and runtime qualification tests」，而它读到的 stderr 尾部被丢弃 —— 容器日志里也是同一句话，运维无从下手 | 引擎输出写进 **worker 自己的日志**（容器日志是运维的诊断入口），对外仍只给一句可安全转述的结论。**不能**把子进程输出直接当消息：`jobs.error` 会经 API 与看板外露，可能带连接串与内网路径（契约见 `test_qlib_worker_preserves_safe_blocker_and_hides_unknown_output`）。**正是这条日志才让上面那条缺陷变得可诊断** |

另外，`data.py:safe_artifact` 现在把「钉住的代次不在磁盘上」报成一条可读的 `PipelineBlocked`（「该运行无法重放，需要重建」），而不是让 `resolve(strict=True)` 抛一个裸的 `FileNotFoundError`。**崩溃与「前置条件不满足」是两件事**，运维该看到的是后者。

## P0 · 阻塞上线

### P0-1 没有任何已训练/已批准模型，平台零产出

**证据**

```bash
curl -s -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8000/api/v1/data-readiness
# day  ready: False | blockers: ['no approved, qualified, unexpired Qlib model']
# 5min ready: False | blockers: ['unverified capabilities: minutes', 'no approved, qualified, unexpired Qlib model',
#                                'no validated Qlib generation', 'daily model baseline unavailable']
```

`/api/v1/models` 为空；`reports` 表只有 3 条 `kind='qlib'` 的**描述性**报告。

**影响**：使用者打开看板看不到任何建议；`My Model Portfolio` 的「接受变更」没有对象；`Low-Price Scan` 没有候选。系统目前唯一能交付的是 Qlib Report 的描述性统计。

**修复（⚠️ 部分解除：链路已通，模型被如实拒绝）**：按[部署说明 · Activation checklist](部署说明.md#activation-checklist)走完：训练 → 20 个健康生产交易日的影子观测 → 人工提升。**前置条件是先解决 P0-2**，否则训练根本起不来。

本轮把 P0-2 解掉之后，训练链路第一次**完整跑通**（`pipeline_runs.state = succeeded`，`prepare` 与 `train` 都 `complete`），并产出了第一个模型：

| 项 | 实测值 |
| --- | --- |
| `rank_ic` | **+0.0370**（此前 Qlib Report 的描述性统计是 −0.0130） |
| `excess_return` | +0.0163 |
| `max_drawdown` | 0.0 |
| 时间切分 | train 2021-06-22..2024-07-31 / valid 2024-08-09..2025-08-22 / test 2025-09-02..2026-09-15 |
| `passed` | **false** → `state = rejected` |

**模型被拒绝是正确行为，不是缺陷** —— 判据里只有一条没过：`historical_pool_coverage_passed = false`。而它的根因是 **P1-4 从数据层传播到了策略层**：`reconstruct_pools` 要求历史池里每只证券的 `risk` 特征有限，`strategy.market_features` 读的正是代次里的 `risk`；公开源没有带日期的风险状态，于是历史上每一天的 `risk` 都是 NaN → `ready` 集合为空 → `coverage = 0` → 池不 `ready` → 模型永不合格。

同一件事还让**模拟账户一笔都没成交**（`net_return = 0.0`、`max_drawdown = 0.0`）——`exclude_risk_names` 是 `Literal[True]`，风险未知就排除，排除干净就没有持仓。所以 P0-1 现在的状态是：

- **已解除**：平台能训练、能评估、能如实拒绝一个不合格的模型（此前连一步都跑不到）；
- **未解除**：仍然没有**已批准**的模型，而唯一卡住它的是一条**产品决策** —— 要么接入带日期的风险/更名公告源（P1-4），要么明确「风险状态不可回溯时，回测是否可以放行未知风险的名字」。**本方案不擅自替使用方做这个决定**：把「未知」当成「无风险」会让回测混入 ST 股，而把它当成「不可交易」就是当前的结果。

**已加的可诊断性**：评估结果现在带 `rejection_reasons`（逐条列出没过的判据）与 `historical_pool_feature_deficits`（每个特征各缺多少只证券），所以运维看到的不再是孤零零的 `passed: false`，而是「`historical_pool_coverage_not_met`，`risk` 缺 298 只」。**「缺什么」决定该修什么**：`risk` 缺是数据可得性问题，`missing_prediction` 缺是模型问题，两者的动作完全不同。

### P0-2 训练路径被「点位风险状态缺失」阻塞（当前死结）

**证据**

```sql
SELECT count(*), min(effective_day), max(effective_day) FROM security_states;
--  5220 | 2026-09-26 | 2026-09-26      ← 全部只有「今天」这一条

SELECT id, kind, status, error FROM jobs WHERE kind='qlib_prepare';
--  179338 | qlib_prepare | blocked | Qlib input coverage 0.0% is below policy; inspect history and security-state coverage.
```

`analysis_target = 2026-09-24`，而风险状态最早只到 `2026-09-26`。`build_generation` 要求状态的 `available_at` 不晚于 K 线当日（`src/quant_platform/adapters/qlib/data.py:276`），于是每根 K 线的 `risk` 都是 NaN → 没有一只证券 `ready` → `coverage = 0.0%` → 流水线阻塞。

**影响**：**无法训练任何模型**，因此 P0-1 无法解除。

**修复（✅ 本轮已修）**

1. **训练接受未知的点位风险状态。** 公开源不发布带日期的更名史，所以**任何**跨越观测日的历史训练集都拿不到点位风险状态 —— 原来要求「每根 K 线的风险特征都有限」，等于要求整段历史都不许训练。现在：`risk` 在无状态覆盖的 K 线上是 **NaN（未知）**，训练接受它，推断不接受（决策日当天的状态是观测得到的，缺了说明状态采集没跑到，那才是真的该挡住）。这同时符合 Qlib 的 NaN 语义（缺失特征交给模型，不丢整只证券）与 QuantMind 的缺列契约（**留 NaN + 显式告警**，绝不静默跳过）。
2. **月度回归缺陷已修。** `security_history` 原来只在**每月 1 日**触发一次，把最新状态钉在当月 1 日；而 1 日 18:30 之前的 `analysis_target` 还是上月最后一个交易日 —— 那个窗口里没有任何状态覆盖决策日，覆盖率会**每月归零一次**。现在调度器对**采集范围**按**决策日**观测一次（`security_history` 是纯本地推导，读主表名称，不消耗任何源配额），月度全表扫描保留，用来覆盖范围之外的历史证券。观测日因此是契约的一部分：`jobs.market.security_history` 接受显式的 `day`，`Market.security_history` 把 `observed_lag_days` / `backfilled` 写进记录，回填永远不可能冒充当日观测。
3. **缺口可诊断。** 覆盖率不足时不再只报一句 `coverage 0.0%`，而是把**排除理由的分布**写进错误：`omissions: missing_current_bar_adjustment_or_point_in_time_security_state=298`，并直接说明该理由的含义。分母同时从「全部上市证券」改为**采集范围内的证券数**（见 P0-3）。
4. **缺口可观测。** 代次 manifest 新增 `coverage_detail`：声明范围、合格数、就绪数、逐项排除理由、点位风险状态的已覆盖/未覆盖只数，以及 `adjusted_window`（每只证券可用会话数）。`data_quality.point_in_time_risk_state` 把同一件事报给运维面板。
5. **仍然做不到的**：`security_states` 没有**带日期的**历史。要让跨越观测日的回测结论可信，必须接入带日期的更名/风险公告源。在此之前，任何跨越观测日的回测结论都必须在报告里标注「风险状态仅覆盖观测日之后」—— 这条限制现在由 `coverage_detail.risk_state` 与 `data_quality` 同时声明。

### P0-3 全市场覆盖远低于生产门槛

**证据**

```sql
SELECT count(DISTINCT symbol) FROM daily_bars;   --  284
SELECT count(DISTINCT symbol) FROM factors;      --  265
SELECT count(*) FROM instruments;                -- 5220
```

默认 `QUANT_HISTORY_SCOPE=index`，只采沪深 300 成分 + 观察篮子。Activation checklist 要求**全市场日线覆盖 ≥ 95%**。

**影响**：不能宣称生产可用；建议只覆盖沪深 300 的一个子集，且该子集还在被 P1-1 的因子深度进一步削减。

**修复（✅ 本轮已修其中「门禁分母」的结构性部分）**

原实现里 `pipeline.create_run` 把**全部上市证券**放进训练宇宙，而采集范围是沪深 300（298 只）：`minimum_coverage` 的下限是 0.95，分母 5220、分子最多来自 298，**上限约 5.7%，无论数据多好都过不去** —— 和之前那个「能力门禁结构性不可满足」是同一类缺陷，门禁测的不是数据而是配置。

- `pipeline.create_run` 的训练宇宙改为**等于采集范围**（复用 `collect.scoped_codes_on`，与采集共用同一份定义，避免两处漂移）；`history_scope=all` 时范围就是全市场，语义不变；范围无法解析时**明确阻塞**，而不是悄悄退回全市场。
- `readiness` 新增一条独立阻塞项：`history scope is 'index'; production acceptance requires QUANT_HISTORY_SCOPE=all with at least 95% full-market daily coverage`。采集范围是**配置**，不是数据缺陷，所以它单列一条，而不是躲在覆盖门禁后面。

**仍待办**：要把覆盖做到**全市场** 95%（生产验收口径），必须把 `QUANT_HISTORY_SCOPE` 从 `index` 切到 `all`，并评估配额（普通请求 20/分钟 → 5220 只一轮约 4.4 小时，靠有进展的续跑任务多轮收敛）与磁盘增长。`readiness` 会把这一条单独报出来（`history scope is 'index'`），不会让它躲在覆盖门禁后面。

**⚠️ 更正上一轮的判断**：上一轮把「298 只成分股里只有 265 只有因子（88.9%）、低于 0.95」归因为**环境约束**（东方财富 K 线主机被拒，复权来源只剩腾讯）。**这个结论是错的。** 本轮把采集跑完之后实测：

```
daily_bars  284 → 299 只
factors     265 → 298 只
代次 market_coverage  88.9% → 98.99%
```

那 33 只缺口不是「源拿不到」，而是**采集没跑完**：新浪给 K 线、腾讯给因子，33 只全部可取。真正的教训是**调度层的幂等性把缺口永久化了** —— 主 `history` 任务的去重键是 `history:<start>:<target>:<北京日期>`，当天已经用过一次，之后无论重跑多少次 `tick` 都不会再入队；续跑任务又有 `REPAIR_LIMIT` 上限。**一个「当天已计划过」的标记，会掩盖一个尚未完成的采集。**

所以：`index` 范围下的覆盖**可以**达到 98.99%，不需要换网络出口；东方财富主机被拒影响的只是**复权深度**（P1-1），不是**覆盖**。P0-3 剩下的只有「把范围切到全市场」这一个决策。

## P1 · 影响结论正确性

### P1-1 复权因子深度远小于分析窗口，且各股深度不一

**证据**

```sql
SELECT endpoint, count(DISTINCT scope) filter (WHERE scope ~ '^\d{4}-') AS dated_scopes, min(scope), max(scope)
FROM datasets GROUP BY 1;
-- history     | 1501 | 2020-07-22 | 2026-09-24
-- factors     |  828 | 2023-04-28 | 2026-09-24     ← 少了 673 个会话
```

代次 manifest 的 `trimmed_unadjusted` 显示每只证券被截掉的会话数从 **61 到 1439** 不等（腾讯前复权约 800 会话封顶，东方财富不可达时没有更深来源）。

**影响**

1. 训练集实际只有约 700–860 个会话，远小于声明的 `QUANT_HISTORY_SESSIONS=1500`；
2. **各股可用深度不同，而深度与上市时间、流动性相关** → 引入选择偏差，不是随机缺失；
3. `QUANT_FACTOR_SESSIONS=500` 的准入只要求「最近连续 500 个会话有因子」，**不会暴露这个偏差**。

**修复（✅ 本轮已修「显式声明」部分）**

- **✅ 已修**：代次 manifest 新增 `coverage_detail.adjusted_window` —— 每只证券可用会话数的 `minimum` / `median` / `maximum`，以及「短于分析窗口」的只数。深度不再埋在 JSON 里，也不再只出现在导出代次（`trimmed_unadjusted`）里。同一条记录里还有 `declared_scope` / `eligible` / `ready` / `omitted_by_reason`，所以「样本面为什么变小」是一个可读的事实，而不是一个百分比。
- **未修（有意为之）**：训练**没有**按「所有候选证券的共同可用窗口」取交集。交集由深度最浅的那只决定，会砍掉绝大部分样本 —— 用一个更小的样本面换取口径一致，代价更大且更容易被误读。当前选择是**如实记录、不静默截齐**，把取舍交给使用方。
- **未修**：`QUANT_FACTOR_SESSIONS` 仍是 500（「能过门禁」的值，不是「研究可信」的值）；更深的复权来源仍未接入，这是本方案最大的单点数据依赖。

### P1-2 上市日期全为 NULL，点位上市过滤退化为「未知即视为已上市」

**证据**

```sql
SELECT count(*) AS instruments, count(list_date) AS with_list_date FROM instruments;  -- 5220 | 0
SELECT value->>'list_dates_verified' FROM settings WHERE key='directory';             -- false
```

只有东方财富发布上市日期，而它在这台机器上不可达（`ProviderError`，宿主机 `curl` 同样 `(52) Empty reply`）。

**影响**：**回测会把上市前的区间当作可交易** —— 这是直接的前视偏差。此外新股上市初期的涨跌幅规则与已上市股不同，限价推导也会错。

**修复（✅ 本轮已修，真实源验证）**

根因不是「公开源不发布上市日期」，而是**被拒的是其中一台主机**。实测：`push2.eastmoney.com`（主表与 K 线）在本网络被网络边缘拒绝，而**同一家东方财富的 `datacenter-web.eastmoney.com` 仍然应答**，且 `RPT_F10_BASIC_ORGINFO` 报表带 `LISTING_DATE`。

1. `EastMoney.listing_dates()` 走数据中心主机分页读取上市日期；
2. `Market._attach_listing_dates()` 在**主表已经发布之后**做补齐 —— 上市日期与证券身份是两个独立的可达性问题：主表可能来自新浪，日期仍能从东方财富补齐。补齐是**尽力而为**，失败不会把已成功的主表拖失败，缺口继续由 `settings.directory.list_dates_verified=false` 暴露；
3. `settings.directory` 新增 `list_dates_count` / `list_dates_filled`，缺口（或它被填平）看得见。

**真实源验证**：主表 5220 只（来源新浪），**5220 只（100.0%）拿到上市日期**，全部由兜底补齐；`SH600000 → 1999-11-10`、`SH600004 → 2003-04-28`。部署后：`settings.directory` 的 `list_dates_verified` 由 `false` 变 **`true`**，`instruments` 5220 行全部有 `list_date`（1990-12-19 ~ 2026-09-22）。

**踩过的坑（值得记下来）**：第一版每页取 500 行，全表要 50 次请求，而普通请求配额是 **20 次/分钟**；第 19 页抛 `Deferred` 后 `except` 直接 `return`，把已经取到的日期**全丢了**。单元测试和宿主机直连都通过，**只有真跑任务才暴露** —— 因为只有任务路径会走配额计数。修复：页大小提到 5000（全表 5 次请求），并且中断时**保留已取到的部分**。

**仍待办**：`list_dates_verified` 目前仍只是记录，未进入就绪门禁；`list_date IS NULL` 在「采集完整性」语境下的 NULL 容忍写法（`list_date IS NULL OR list_date <= day`）是对的，在「回测可交易性」语境下是错的，两处仍需区分。

### P1-3 沪深 300 成分是**无日期**快照 → 幸存者偏差

**证据**

```sql
SELECT jsonb_array_length(value->'symbols'), value->>'dated' FROM settings WHERE key='index_members';
--  298 | false
```

**影响**：用**今天的**成分股回测历史 = 幸存者偏差；期间被剔除的成分不在样本里，而它们的表现通常更差。`source_gaps` 只检查「有没有成分」，不检查是否点位。

**修复**：需要**带日期的成分历史**。公开源不提供时，可选退路是「用当时上市且非风险警示的全市场」做近似，并在报告里**显式声明这是近似**；或引入付费点位成分源。**不要把无日期快照当点位数据使用**，也不要因为它「看起来是对的」就跳过这一条。

### P1-4 风险警示/退市状态不可回溯

**证据**：`security_states` 5220 行全部 `effective_day=2026-09-26`、`point_in_time=false`、`observed=true`；`Market.security_history` 的 docstring 明说「公开源不发布有日期的更名史，状态从观测当天开始」。

**影响**：历史上任何 ST/退市风险都无法还原 → 回测里 ST 股的 5% 涨跌幅、可交易性、以及「风险警示股被扫描策略排除」这条规则都会算错。

**修复**：同 P1-2，需要带日期的公告来源。在此之前，任何跨越观测日的回测结论都必须在报告里标注「风险状态仅覆盖观测日之后」。

**⚠️ 本轮升级为「阻塞 P0-1」**：这条原来被当成「回测结论要加注」的软约束，实测下来它会**直接卡住模型批准**。链路是：代次里历史 K 线的 `risk` 是 NaN → `strategy.market_features` 读到 NaN → `strategy` 把该证券记为 `risk_unverified` 并排除 → 模拟账户一笔都不成交（`net_return = 0.0`、`max_drawdown = 0.0`）→ `reconstruct_pools` 的 `ready` 集合为空 → `coverage = 0` → `historical_pool_coverage_passed = false` → **模型永不合格**。

所以它现在不是一个「加注即可」的风险，而是一个**必须先做的产品决策**：

| 选项 | 后果 |
| --- | --- |
| 接入**带日期**的更名/风险公告源 | 唯一能让回测与策略都正确的做法。免令牌源目前找不到；需要付费源或交易所公告解析 |
| 明确「风险状态不可回溯时，回测是否放行未知风险的名字」 | 放行 = 回测会混入当时的 ST 股，**必须在报告里显著声明**；不放行 = 当前状态（没有模型） |
| 缩小评估窗口到「有状态覆盖」的区间 | 与观测日起算冲突：观测日之后还没有足够长的样本 |

**本轮已做的只是把结论说清楚**：评估结果新增 `rejection_reasons` 与 `historical_pool_feature_deficits`，所以「模型为什么被拒」现在是可读的（`historical_pool_coverage_not_met`，`risk` 缺 298 只），而不是一句 `passed: false`。**没有擅自改判据**：把「未知」当成「无风险」会污染回测，而把判据放宽到能过，正是这份文档反复在反对的那种「为了让门禁通过而改门禁」。

### P1-5 `constraints` 是本地推导，`suspended` 恒为 `False`

**证据**：`CAPABILITY_SOURCES["constraints"] = ("derived",)`；`Market.constraints` 里 `"suspended": False` 是硬编码；`limit_rate` 按板块建模（科创板/创业板 20%、主板风险警示 5%、其余 10%），但**未处理新股上市首日、复牌首日等特殊规则**。

**影响**：停牌只能靠「成交量为 0」间接识别（`tradable = not suspended and volume > 0`）；特殊首日规则下涨跌停价会算错，进而影响可交易性与成交假设。

**修复（✅ 本轮已修「虚假断言」部分）**

参考 **Qlib 的约定**：停牌在数据里就是 **NaN**（OHLCV 与 factor 置空），不是一个布尔列 —— 因为布尔列一旦拿不到源，就只能填一个假的默认值。据此：

1. `Market.constraints` 不再写 `suspended: False`，改为 `suspended: None` + `suspended_source: "unavailable"`：**「不知道」不再冒充「已确认可交易」**；
2. `jobs/diagnostics.py` 的排除条件改为「约束记录缺失 **或** 上游明确报出停牌」，真正的停牌交给成交量判定，不再把字段值非真当成停牌；
3. `analysis/market_report.py` 新增 `suspended_known` 标记列，把「0 只停牌」与「停牌数未知」分开：没有可信标记时报告 `available: false` 而不是报 0。

**仍待办**：新股上市首日、复牌首日等特殊规则仍未建模；限价仍是本地推导值，需在报告里继续声明。

**影响**：样本面无声缩小，**没有任何告警**。

### P1-7 Qlib Report 的 IC 为负，容易被当成选股依据

2. 把「IC 方向是否与假设一致」纳入模型批准流程的人工复核项；
3. 排查方向性原因（标签对齐、复权基准、动量定义）——**注意这可能是真实的短期反转效应，不一定是代码缺陷**，需要先给出解释再决定是否动代码。

## P2 · 运维、安全与可用性

### P2-1 单机部署：备份与主库在同一失败域

**证据**：[部署说明](部署说明.md#运行备份与关闭)明确写「本地 bundle 在 `quant-platform_local-backups`；另一个目录或 Docker 卷**不自动是另一个失败域**」；`QUANT_BACKUP_REPLICA_ROOT` 默认未设置，只保留主备份。

**影响**：主机或磁盘故障会同时丢掉主库与备份；「有备份」不等于「能恢复」。

**修复**：设置 `QUANT_BACKUP_REPLICA_ROOT` 指向**真正的不同故障域**（另一台主机 / 对象存储），加密存储；定期用 `restore-check` **从异地包**演练，并记录 RPO/RTO（`--fault-at`）。保留策略是「7 个已提交的自有 bundle」，不是「保留两代」。

---

### P2-2 `notify` 未配 webhook 则告警不外送

**证据**：`QUANT_NOTIFY_WEBHOOK` 默认空；告警只写 `alerts` 表，看板需要主动打开才看得到。

**影响**：没人盯着看板时，采集失败、能力阻塞会被漏掉。

**修复**：配置 webhook，或把 `alerts` 表接入既有外部监控。至少对「`maintenance` 失败」「能力从 verified 掉到 blocked」「任务连续失败」三类加外送。

---

### P2-3 单一操作员令牌，无多用户与身份审计

**证据**：API 只有一个 bearer token（`hmac.compare_digest` 比对，常量时间，这点是对的）；请求观测只记 `path/status/at`，**不记调用者**。

**影响**：无法回答「谁接受了哪次变更、谁提升了哪个模型」；令牌泄露即等于全权。

**修复**：短期严格执行轮换流程并确保令牌不落进日志；中期引入多用户/角色，并把调用者写进已有的 `audit` 表。当前是**单操作员开发部署**，不要把它的权限模型直接搬到多人环境。

---

### P2-4 令牌接口无速率限制

**证据**：`/api/v1/*` 只挂了一个 `auth` 依赖，没有失败计数、退避或限流；`/health/live` 无认证（用于存活探针，属正常）。

**影响**：端口一旦对外暴露，可被暴力猜测令牌。

**修复**：保持只绑 `127.0.0.1`（现状）；确实需要对外时，**必须**前置反向代理做 TLS 与限流，并考虑加失败退避。

---

### P2-5 `maintenance` 的分区 DDL 依赖 `0010` 的白名单函数

**证据**：迁移 `0010` 用 `SECURITY DEFINER` 暴露 `ensure_range_partition` / `retire_empty_partition`，只允许 `quotes` / `alerts` / `minute_bars` 三张表；分区父表属主是迁移用户，工人以 `quant_worker` 连接。

**影响**：迁移未应用或函数被回收时，T+1..T+3 分区不会创建，**故障要到当天才暴露**。

**修复**：把「T+1..T+3 分区存在性」纳入 `status` 与告警；`maintenance` 任务失败必须外送（见 P2-2）。

---

### P2-6 `quotes` / `minutes` 只能在盘中会话验证

**证据**：能力表中这两个端点 `schema_verified=false`；采集受 `session()` 门禁，非交易时段不会运行。

**影响**：运维在周末看到它们为 `false`，容易误判为故障。

**修复**：本手册第 9 节已说明；建议在看板「服务与接口」页对这两个能力加「仅在交易时段验证」的说明文案。

---

### P2-7 改代码必须重建镜像，容易漏

**证据**：容器内 `quant_platform` 来自 `site-packages`（`/app/.venv/lib/python3.11/site-packages/quant_platform`），**没有源码 bind mount**；本轮就曾因为没重建镜像导致修复「看起来已上线但实际没生效」。

**影响**：改了代码却以为已上线，排障时会得出错误结论。

**修复**：发布流程固定 `qc build <服务>` + `qc up -d`，并把「容器启动时间 vs 源码最后修改时间」作为发布检查项。

---

### P2-8 `uv.lock` 与 `pyproject.toml` 不同步会静默丢依赖

**证据**：[部署说明](部署说明.md#开发与测试)明确写 `uv sync --frozen` 严格按 `uv.lock`，**声明但锁文件里没有的依赖会被静默跳过**。

**影响**：`pytdx` 这类可选源会以「模块不存在」的形式**在运行时**才暴露，而且降级链会安静地少一个源。

**修复**：CI 里加 `uv lock --check`；镜像构建前校验锁文件；把「四个源都在」纳入 `doctor` 的期望值（现在缺源只是少一个候选，不报错）。

---

### P2-9 五分钟链路从未验证

**证据**：`minutes` 能力未验证；`qlib_intraday` 从未执行过；`minute_bars` 只有 default 分区加滚动分区。

**影响**：`5min` 就绪恒为 false，且「分钟容量是否够」这个问题没有任何实测数据。

**修复**：在真实交易日按 Activation checklist 走一遍分钟链路，并在**目标主机**上测并发训练延迟与发布截止时间。

## P3 · 观测与语义（会误导判断）

### P3-1 代次 `coverage` 按全部上市主表计

**证据**：`coverage` 有 5220 条，其中 265 条有覆盖日期、19 条有 K 线无因子、4936 条无 K 线，全部记为 `missing_adjustment_or_bars`。

**影响**：运维看到「4955 条缺失」会以为采集坏了，实际是默认范围本来就不采它们。

**修复（✅ 本轮已修「语义分离」部分）**：`coverage` 字段语义不变（消费端只读日期形态值），新增 `coverage_detail` 把两个分母分开写清楚：

```json
{"scope_mode": "index", "declared_scope": 298, "eligible": 298, "ready": 265,
 "omitted_by_reason": {"missing_daily_history_or_adjustment": 33},
 "universe": 5220, "universe_coverage": 0.0508, "risk_state": {...}, "adjusted_window": {...}}
```

`declared_scope` / `eligible` / `ready` 是**门禁用的**那一组（采集范围）；`universe` / `universe_coverage` 只是诊断——采集范围默认就是沪深 300，这个数天然很低，**绝不能当门槛**。`omitted_by_reason` 让「4936 条缺失」这类噪声与实际缺口分开。**仍未做**：看板上的展示（见 P3-1 原文）。

---

### P3-2 非交易时段 `data_health` 长期为 `degraded_or_unavailable`

**证据**：`data_health = "fresh" if total and verified == total and directory_fresh else "degraded_or_unavailable"`；`verified` 按源时间戳判定。

**影响**：周末与长假期间总览一直告警，**与真实故障无法从这一个字段区分**，会削弱告警的可信度。

**修复（✅ 本轮已修）**：新增 `operations.market_health()`，把「没有新行情」拆成三种状态：

| `data_health` | 含义 |
| --- | --- |
| `fresh` | 全部证券都有验证过的行情，且主表目录新鲜 |
| `quiet_outside_session` | 目录新鲜、当前**不在交易时段**（休市/盘前/午休），因此没有新行情是**预期**的 |
| `degraded_or_unavailable` | 其余情况：交易时段内验证不足，或目录本身不新鲜，或**日历未验证** |

日历未验证（`calendar_open` 返回 `None`）时**不猜**「休市」，仍报降级 —— 「不知道」不能冒充「已确认」。真实故障与周日因此不再共用同一个值。

以下两条是本轮发现并修复的**结构性缺陷**，已在真实栈验证，细节见[系统验证报告](系统验证报告.md#deployed-stack-defect-closure-and-end-to-end-run--2026-092627)：

| 缺陷 | 症状 | 修复 |
| --- | --- | --- |
